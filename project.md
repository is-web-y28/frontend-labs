# Лабораторные работы 5–7. Собственный проект

## Задача

Сделать проект на свою тему. Он собирается в три этапа: ЛР 5 — разметка, ЛР 6 — стилизация, ЛР 7 — интерактив. В следующем семестре к проекту пишется бекенд.

Проект в том же репозитории в **отдельной** ветке (например, `project`)

## Согласование темы

До начала разработки тема согласуется с практиком. Без согласования работа не принимается.

На согласование приносите:

- описание темы в 1–2 абзаца: что за продукт и для кого
- доменную модель: сущности, их поля и связи (можно диаграммой в Mermaid)
- макет основных экранов — в Figma, от руки или сгенерированный (Claude Design, Figma Make, v0 и т.п.)

В ЛР 7 в проект добавятся авторизация через внешних провайдеров и обмен данными по WebSocket, поэтому тема должна предполагать личные данные пользователя и события в реальном времени.

Примеры тем:

- **Трекер задач для команды** — проекты, задачи, участники, комментарии; в реальном времени — смена статусов и новые комментарии
- **Бронирование переговорок** — помещения, слоты, бронирования; в реальном времени — занятость слотов
- **Барахолка** — объявления, категории, пользователи, переписки; в реальном времени — чат продавца и покупателя
- **Онлайн-квиз** (как Kahoot) — квизы, вопросы, комнаты, ответы; в реальном времени — ход игры и таблица лидеров
- **Клуб чтения** — книги, клубы, встречи, обсуждения; в реальном времени — обсуждение
- **Запись к мастеру** — мастера, услуги, слоты, записи; в реальном времени — освободившиеся слоты
- **Общий вишлист или список покупок** — списки, позиции, участники; в реальном времени — отметки «куплено» и «забронировано»

Своя тема **приветствуется**. Если сделаете то, чем будете пользоваться сами или ваши знакомые — это большой плюс.

## Стек технологий

**База:** любой компонентный фреймворк (React, Vue, Angular, Svelte и т.п.), TypeScript. Фреймворки, которые не разбираются на лекциях, — на вашу ответственность, как в ЛР 4

**Библиотека компонентов** — на выбор, как в ЛР 4 (для Svelte — например, [shadcn-svelte](https://www.shadcn-svelte.com/), [Skeleton](https://www.skeleton.dev/), [Flowbite Svelte](https://flowbite-svelte.com/)). Выбирается в ЛР 5, потому что из её компонентов строится разметка.

## Общие запреты

1. Устаревшие подходы фреймворков: классовые компоненты в React, Options API во Vue, `NgModule` в Angular, синтаксис Svelte 4 (`export let`, `$:`) в Svelte
2. Работа с DOM через `document.querySelector` и аналоги
3. Второй ui-kit

## ЛР 5. Разметка

Структура приложения, компоненты и разметка всех экранов на статических данных. Внешний вид не оценивается.

### Структура

- Доменная модель описана типами TypeScript в одном месте: минимум три сущности со связями (один-ко-многим, многие-ко-многим), часть сущностей принадлежит пользователю
- Данные — статические фикстуры, типизированные доменной моделью. Фикстуры подключаются на уровне страниц, остальные компоненты получают данные через props
- Свёрстаны все экраны из макета, включая страницу входа с кнопками провайдеров (без логики)
- Маршрутизация между страницами, страница 404
- Повторяющиеся части интерфейса — отдельные компоненты: карточка сущности описана один раз и используется везде
- Для списков свёрстаны состояния загрузки, ошибки и пустого результата
- `key` в списках — id сущности, не индекс

### Семантика и доступность

- На каждой странице `header`, `nav`, `main`, `footer` там, где они нужны по смыслу
- Один `h1` на страницу, уровни заголовков без пропусков
- Навигация — ссылки, действия — кнопки
- Перечисления — `ul` / `ol`, табличные данные — `table`
- Формы создания и редактирования всех сущностей: у каждого поля есть `label`, связанные поля сгруппированы в `fieldset` с `legend`, у `input` правильный `type`, ограничения заданы атрибутами (`required`, `minlength`, `pattern` и т.п.)
- У изображений осмысленный `alt`, у декоративных — пустой
- Даты — в `<time datetime="...">`

В README.md: тема, доменная модель, ссылка на макет, команды запуска.

### Запрещено

1. Кликабельные `div` и `span` вместо `button` и `a`
2. Данные, захардкоженные прямо в разметке компонентов

## ЛР 6. Стилизация

Стилизовать проект по согласованному макету.

**Стилизация [на выбор]**: CSS Modules, Tailwind, styled-components, emotion, SCSS и т.п. **При выборе подхода надо суметь объяснить выбор: назвать плюсы и минусы**

### Требования

- Интерфейс соответствует макету
- Дизайн-токены (цвета, отступы, типографика, скругления) заданы в одном месте: темой ui-kit или CSS-переменными. В компонентах нет захардкоженных цветов и размеров
- Тема ui-kit настраивается через его механизм темизации, а не переопределением внутренних классов
- Светлая и тёмная темы — по желанию
- Интерфейс адаптивный
- У интерактивных элементов есть состояния `hover`, `focus-visible`, `active`, `disabled`
- Стили изолированы: CSS Modules, scoped-стили, инкапсуляция Angular или методология именования

### Запрещено

1. `!important`
2. Инлайн-стили, кроме значений, вычисляемых во время работы

## ЛР 7. Интерактив

Подключить проект к API, добавить авторизацию через внешних провайдеров и обмен данными по WebSocket.

API и WebSocket — ваши собственные, по контракту, который вы описываете сами. В этом семестре всё работает на моках, в следующем те же контракты реализуются на бекенде. Переход на настоящий сервер не должен требовать переписывать компоненты.

Можно использовать HTTP-клиенты (axios, ky) и библиотеки для серверного состояния (TanStack Query, Pinia Colada и т.п.).

### Данные и API

- Контракт API описан в репозитории: OpenAPI или Markdown с эндпоинтами, параметрами и типами ответов
- Весь контракт реализован на [MSW](https://mswjs.io), включая ошибки (400, 401, 403, 404). Фикстуры из ЛР 5 переезжают в моки
- Источник данных переключается через переменные окружения: режим `mock` / `prod` и адреса API и WebSocket для `prod`. В режиме `mock` запускается MSW, в остальных запросы уходят по адресу из переменных
- Все требования ЛР 4: четыре состояния списков, `debounce` в поиске, пагинация или бесконечная прокрутка, создание, редактирование и удаление с подтверждением, уведомления о результате операций
- Фильтры и пагинация хранятся в URL: перезагрузка и кнопка «Назад» сохраняют состояние
- Ошибки сервера при отправке формы показываются у формы, введённые данные не теряются

### Авторизация

- Вход минимум через два провайдера (GitHub, Яндекс ID, VK ID, Google и т.п.) по схеме OAuth 2.0 Authorization Code
- Страница обратного вызова (`/auth/callback`) проверяет параметр `state` и передаёт `code` на бекенд; обмен кода на сессию сейчас выполняет мок
- Логика авторизации вынесена в отдельный модуль; компоненты не знают, мок это или настоящий сервер
- Текущий пользователь определяется запросом к API (например, `GET /me`), токены в `localStorage` не хранятся
- Часть страниц доступна без входа; при переходе на защищённую страницу — вход и возврат туда, откуда пришёл
- Ответ 401 от любого запроса переводит приложение в состояние «не авторизован»
- Есть выход

### WebSocket

- Минимум одна функция в реальном времени, вытекающая из темы: чат, уведомления, обновление статусов, live-обновление списка. Что именно работает в реальном времени, фиксируется при согласовании темы
- Нативный `WebSocket`, на моке — [WebSocket API в MSW](https://mswjs.io/docs/websocket)
- Сообщения в JSON с полем `type`, все типы сообщений описаны
- Соединение одно на приложение: открывается после входа, закрывается при выходе
- При обрыве — переподключение с растущей задержкой, состояние соединения видно в интерфейсе
- Входящее событие обновляет данные без перезагрузки и без дублей

В README.md добавьте ссылку на контракт API.
